# Plan: the pipeline writes the corpus

Status: proposed 2026-11-25. P1 and P2 are built on `feat/corpus-export-laws`, P3 on `feat/corpus-export-collections`, P4 on `feat/corpus-export-drafts`, P5 on `feat/corpus-export-catalog`, P6 on `feat/corpus-export-search`, P7 and P8 on `feat/corpus-release`; P9 on `feat/corpus-comparisons`.

## What changes

`hukum-bersih export-corpus <dir>` (Python, in `pipeline/`) writes the whole web corpus from `data/`: law, collection and draft JSON, the comparison records, the catalog and listings, and the Pagefind index. Its output is a release directory that `web` reads directly in dev (`HUKUM_CORPUS_DIR`) and that CI uploads to R2 unchanged. The TypeScript export scripts in `web/scripts/` are deleted, and `web` stops importing Astro's `web/src/lib/` at build and request time. `route-snapshot.sh` stays as the test tool.

The output is byte-identical to today's. The release id hashes every file in a release, so the proof for every PR is the same check: the Python export gives the same release id as the TypeScript export at that PR's base.

Settled by running before writing this plan (2026-11-25):

- Pagefind has an official Python package at 1.6.0, the same version as the JavaScript one, with `add_custom_record` and `write_files`.
- Word diffs match. Python `diff-match-patch` (20241021) and `@sanity/diff-match-patch` produced identical output on 400 changed paragraph pairs from the two drafts of RUU Perampasan Aset, using the same token encoding as `web/src/lib/compare.ts`.

- Diff engine (operator: use an existing fast native engine, not our own port). Measured 2026-11-25 on the same 400 pairs and token encoding: pure Python `diff-match-patch` 383 ms (400/400 identical to JavaScript); `rapidiff` 0.3.0 (Rust `similar` through PyO3, a prebuilt wheel on Python 3.14) Myers plus `diff-match-patch`'s semantic cleanup 61 ms (379/400 identical; of the 21 that differ, 9 have fewer fragments and changes, 11 have more, 1 the same); `rapidiff` without the cleanup 31 ms (4/400, fragmented); `similar-rs` 32 ms (4/400); `fast-diff-match-patch` (C++) 57 ms (397/400) but no wheel for Python 3.14, and `diff_match_patch-python` also fails to build. The export uses `rapidiff` Myers followed by the semantic cleanup. So comparison word diffs are not byte-identical to the TypeScript export. P4 and P9 prove that pairing, counts, anchors and every non-diff byte are identical, report how many diffs changed, and measure the total diff time.

- Native binding, decided after P9 (2026-11-25). A full export makes 13,311 `word_diff` calls, which take 2.56 s in total, 2.0% of the 126 s export. A binding of our own could save at most those 2.56 s, less than compiling it in CI would cost, so there is none. Revisit if the word-diff share of the export passes about 10%. Larger wins are elsewhere: laws and collections each parse the same base texts, and the Pagefind write takes 47 s.

## PRs in landing order

```
P1 harness ──► P2 laws ──► P3 collections ──► P4 drafts ──► P5 catalog+listings ──► P6 search ──► P7 release+CI ──► P8 delete TS exports
                                   └──────────────► P9 precompute law and collection comparisons
```

Every PR branches from the previous one's merge into `feat/solid-reader`, so they land in order. Only P9 also waits for the `uisdk` branch, because it edits the collection pages that branch is changing.

### P6 Search index

- [x] Depends on: P2 and P4.

- [x] Result: `pagefind/` written last by `export-corpus`: one record per pasal, the opening, the closing and each Penjelasan entry that says more than "Cukup jelas" (75,749 records from 1,915 documents), `maxFragments` 2000.
- [x] Verification: done 2026-11-25. `compare_corpus.py <ts> <py> --under pagefind` gives 2481 identical, 0 differing, 0 missing, 0 extra, from two separate Python runs; a full compare on the rebased tree (with P5) gives 4673 identical and the one comparison that differs only in word-diff grouping (`--word-diff-parts`). Pagefind's Python and JavaScript runtimes write the same bytes: the record inputs of the TypeScript export (url, content, meta, in order) fed to the Python package also give 0 differing files. Pagefind numbers its pages in the order it receives them, so that order is part of the bytes: the TypeScript export took it from `glob` (laws by path, last first, then the drafts), which depends on the file system, and `SearchRecords` keeps that order whatever order the pages are added in. The anchors a record opens are checked against the ids in the exported reader text of 14 real laws (`tests/test_corpus_search.py`). Size: `pagefind/` is 35.5 MB in 2,481 files, as in the TypeScript export. Time: search adds about 56 s to the export (9 s building records, 47 s in Pagefind); the full export took 120 s on 8 cores. The package's own reader sleeps 0.1 s before each reply, which caps it at 10 records a second (two hours for this corpus), so `pagefind_index.py` overrides that one loop; the version is pinned for that reason.
